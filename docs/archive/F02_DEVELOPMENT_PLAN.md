## 1. 결론과 범위

첨부된 「2026년도 NCS학습모듈 검수 확인서」 HWPX의 본문 XML을 읽어 **10개 구성요소, 54개 체크항목**을 확인했다. 여기서 ‘참고 자료’는 첨부 검수표 전체로 해석했다. 검수표 안의 ‘참고 자료’ 구성요소 ①~④도 아래에서 별도로 분석한다.

54개 모두 검수 지원 기능의 대상으로 삼을 수 있지만, 전체를 자동으로 적합/부적합 확정하는 개발 목표는 부적절하다. 정확 비교·개수·번호·필수 항목은 규칙으로 검사하고, 외부 기준·페이지·이미지 정보가 필요한 항목은 입력을 확보한 뒤 검사하며, 의미·교육적 적절성은 근거를 제시하고 사람이 확정한다.

(작성 시점 기준) 현재 저장소에는 위치 5개, 차례 5개, 개요 5개, 필요 지식 8개, 합계 **23개 원문 항목에 대응하는 규칙이 등록**되어 있다. 나머지 31개는 독립 규칙이 미등록이다. 23/54는 항목 등록 범위이며 자동화 완성도나 정확도가 아니다. 예를 들어 개요 ②는 개수만 검사하고 ‘구체적인 과목명’인지는 검사하지 않는다.

이번 산출물은 판별 및 기획 문서다. 검수 엔진의 변경·실행, 원고 수정, 공식 NCS 데이터 조회는 수행하지 않았다. 첨부 파일의 ‘직접 수정 가능’ 표시는 원문 메타데이터이며 자동 수정 지시로 취급하지 않았다.

## 2. 분류 기준

- **A 규칙 검사**: 구조가 정상적으로 추출되고 기준 입력이 있으면 명시적인 조건으로 판정할 수 있다.
- **B 조건부 검사**: 공식 기준 데이터, 승인된 양식, 렌더링 또는 원본 대조 자료를 확보해야 자동 판정 범위가 성립한다.
- **C 검수 보조**: 자동 탐지·추천은 가능하지만 의미·맥락·완전성에 대한 최종 판단은 사람이 한다. 개수나 종결형 같은 하위 조건은 자동 검사한다.

아래 분류는 항목 전체의 요구를 기준으로 한다. ‘등록’은 현재 규칙이 있다는 뜻이며 전체 요구의 충족을 보증하지 않는다. ‘신규’는 독립 규칙 미등록을 뜻한다. ‘재사용’은 기존 파서를 활용할 수 있다는 설계 제안이다.

## 4. 먼저 보완할 기존 구현

1. **부분 검사와 항목 전체 적합을 분리한다.** 개요 ②는 개수만 맞아도 현재 적합을 낼 수 있다. 개요 ⑧도 의심 패턴이 없으면 명사형을 적합으로 처리한다. 자동 검사한 조건과 사람 확인이 남은 조건을 각각 기록해야 한다.
2. **F02만으로 확정할 수 없는 정책을 분리한다.** 필요 지식 ⑧ 코드에는 F14 형식, 표 출처의 선택 처리 등 별도 정책이 있다. 이번에 제공된 자료는 F02이므로 승인된 F14·편집 지침을 확보해 근거와 버전을 연결해야 한다.
3. **미검사와 판단불가를 유지한다.** 기준 자료 미제공, 추출 실패, 지원하지 않는 서식은 적합이 아니다. 항목 자체가 적용되지 않는 경우와 검사 자료가 부족한 경우도 구분한다.
4. **통합 요소·순서 예외를 ID 기반으로 처리한다.** 줄 순서만으로 연결하면 통합·분할·이름 변경 시 잘못된 비교가 발생한다. 원문 값과 비교용 정규화 값을 함께 보관한다.
5. **문단 번호를 페이지로 표시하지 않는다.** 현재 Document는 섹션·문단·표·이미지 이름을 보유하고 실제 페이지 좌표는 보유하지 않는다. 페이지 검수에는 별도 렌더링 모델이 필요하다.

## 5. 개발 구조와 사용자 흐름

권장 흐름: 원고·계획서 입력 → 문서 형식/버전/추출 상태 확인 → 문서 구조와 기준 자료 연결 → 규칙 검사 → 필요할 때 렌더링·OCR 검사 → 근거와 수정 제안 제시 → 검수자 확정 → 이력 저장.

기존 구조를 확장한다.

- `ncs_core.manuscript`: 수행 내용, 교수·학습 방법, 평가 준거/방법/피드백, 참고 자료의 공통 구조 추출. 섹션·문단·표·셀 위치를 유지한다.
- 각 검수 패키지: 검사 정책·예외·판정. 신규 영역은 `ncs_performance`, `ncs_teaching`, `ncs_evaluation`, `ncs_references`, `ncs_publication`, `ncs_misc` 같은 독립 엔진으로 추가할 수 있다. 명칭은 제안이다.
- 렌더링/OCR: 기존 표준 라이브러리 기반 엔진과 분리한 선택 어댑터로 구현한다. 입력 해시·변환 환경·페이지 좌표를 기록하고 동일 원고의 렌더링인지 확인한다.
- 기준 자료: 코드·명칭·수준·적용 연도/버전·승인 출처를 가진 기준표를 가져온다. 초기에는 승인된 파일 입력이 가능하며 실시간 사이트 연동을 전제로 하지 않는다.
- 결과: 원문 항목 ID, 하위 조건, 검사 여부, 판정, 원고 근거, 기대값, 위치, 규칙 버전, 기준 자료 버전, 검수자 확정과 사유를 저장한다. 자동 결과와 사람의 최종 결과는 덮어쓰지 않고 구분한다.
- UI: 전체 54개 기준의 검사/미검사/판단불가 범위를 보여주고, 지적사항에서 해당 문단이나 렌더링 위치로 이동하게 한다. AI 보조 결과에는 확인 대기 상태를 표시한다.

엔진 등록 시 기존 `docs/CONVENTIONS.md`에 따라 서비스 레지스트리, 웹 API 검수 종류, 화면 목록을 함께 반영한다. 공통 추출을 위해 다른 검수 엔진을 직접 import하지 않는다. 저장 스키마 변경이 필요하면 새 마이그레이션을 추가한다.

## 6. 개발 단계·우선순위·완료 기준

일정은 개발자 1명과 검수 담당자의 정기 검토, 대표 원고와 기준 자료 제공을 가정한 초기 추정이다. 실제 원고의 양식 편차와 변환 환경 검증 후 재산정한다.

| 단계 | 예상 작업 기간 | 구현 범위 | 완료 기준 |
|---|---|---|---|
| P0 기준 확정·기존 범위 점검 | 3~5일 | 54개 항목과 하위 조건 등록, 기존 23개 검사 범위 확인, 실제 문서 정답셋 준비 | 모든 항목에 자동/사람 검사 범위·기준 자료·미검사 사유 정의 |
| P1 텍스트 기반 MVP | 2~3주 | 수행 ①④, 교수·학습 ①③의 개수, 평가 ①②③ 및 ⑤의 연결·개수, 기타 ⑦ | 실제 문서의 정상/오류 사례에서 근거 위치와 기대값을 제공하고 불완전 항목을 적합으로 확정하지 않음 |
| P2 기준 데이터·참고 자료 | 2~3주 | 개요 ③④⑦, 참고 자료 ①~③의 형식·연결 검사, 이력/판권 ① | 기준 버전 추적, 누락/다대일/자료 유형 예외 처리, 자료 없을 때 판단불가 |
| P3 페이지·이미지 | 2~4주 | 차례 ⑦, 기타 ①②⑤⑥의 측정 가능한 조건 | 동일 원고 렌더링 확인, 인쇄 쪽수 매핑, 출력 크기·해상도 측정, 변환 실패 분리 |
| P4 의미·시각 보조 | 2~3주 | 행동명사/동사, 안전 구체성, 상표·인물·작업 표시줄, 평가 적절성, 저화질 텍스트 이미지 | 후보 위치·이유 제시, 사람 확정 흐름, 항목별 정밀도·재현율 보고 |

**첫 배포는 P0+P1의 약 3~4주 범위를 권장한다.** 후속 P2~P4는 데이터 준비와 효과 검증 후 순차 결정한다. 상기 전체 일정은 운영 배포·외부 연동 계약 등을 포함한 확정 견적이 아니다.

참고 자료 구성요소만 우선 개발한다면, ② 유형별 서지 형식 → ③ 분류·정렬 → ① 본문 인용 연결 → ④ 구모듈 재인용 추적 순서를 권장한다. 마지막 항목은 구모듈과 출처 이력이 없으면 검수 보조 수준에 머문다.

## 7. 검증 계획

- 실제 원고·계획서 쌍을 최소 10~20건 확보하는 것을 초기 목표로 한다. HWP/HWPX, 신규/개선, 통합 능력단위, 비정형 표, 이미지 많은 문서를 포함한다. 이 수량은 파일럿 목표이며 충분한 정확도의 보증이 아니다.
- 검수자가 항목별 정답과 근거를 작성하고, 모호한 사례는 두 사람이 합의한다. 개발에 사용하지 않은 문서를 별도 평가셋으로 둔다.
- A 항목은 누락/중복/순서 변경/경계값을 의도적으로 넣은 사례로 판정과 근거 위치를 검증한다. 개요 5개/6개, 핵심 용어 10개/11개, 교수·학습 2개/3개, 평가 방법 1개/2개를 포함한다.
- B 항목은 자료 부재·버전 불일치·변환 실패·쪽번호 재시작·이미지 깨짐·크기 변경 사례를 검증한다. 정보를 못 읽은 상태에서 통과시키지 않는 것을 필수 조건으로 둔다.
- C 항목은 정밀도(지적 중 실제 오류 비율)와 재현율(실제 오류 중 발견 비율)을 분리한다. 파일럿 출시 목표 예시로 규칙 지적 정밀도 95% 이상을 검토하되 항목별 사례 수와 오탐/미탐을 함께 공개하고 실제 결과로 조정한다. 의미·시각 보조는 자동 적합 판정에 사용하지 않는다.
- 코드 변경 후 기존 골든·엔진 계약·계층·서비스·웹 테스트를 실행한다. 신규 정책은 기존 결과가 바뀌는 이유를 기록하고, 정답 파일은 의도된 변경에 한해서 갱신한다.
- 최종 파일럿에서는 검수 시간, 잘못된 부적합, 놓친 오류, 판단불가 비율을 측정한다. 단순히 구현 항목 수가 늘었다는 이유로 배포 완료로 판단하지 않는다.
