# F02 오판정 사례 분석

판정이 기대와 다른 사례를 받아 **재현 → 층 가르기 → 수정 사양** 순으로 진행한다.
산출물은 `_workspace/01_analyst_spec.md` 하나이고, 코드는 고치지 않는다.

## 1. 사례를 한 줄로 고정한다

분석 전에 사례마다 아래 다섯 가지를 채운다. 하나라도 비면 재현이 아니라 추측을 하게 된다.

| 칸 | 예 |
|---|---|
| 구성요소·번호 | 차례 ③ |
| 원고(와 개발계획서) 경로 | `samples/…/LM…hwpx`, `samples/…/개발계획서_….hwp` |
| 실제 판정 | 부적합 |
| 기대 판정 | 적합 |
| 기대의 근거 | 기대 표 행 / 검수자 판단 / 수정사항.md |

사례 출처별로 읽는 법:
- **`batch_compare.py` 대조 결과(마크다운)**: '미탐'은 기대 부적합인데 못 잡은 것, '오탐 후보'는 조작하지 않은 항목이 부적합인 것, '원본 자체 부적합'은 조작 전 원고가 부적합인 것이다. '원본 자체 부적합'은 진짜 지적일 수도 규칙 오탐일 수도 있어 사례마다 갈라야 한다.
- **기대 표(`scripts/batch_expected_*.tsv`)**: 비고의 '부수'는 조작이 다른 항목에 번지는 기대, '서식'은 텍스트 규칙으로 못 잡는 조작이다. 기대 표도 사람이 옮긴 것이라 틀릴 수 있다.
- **사용자 서술**: 원고 경로와 기대의 근거를 되묻지 말고 먼저 `samples/`와 대화 맥락에서 찾는다. 못 찾으면 그때 반환 메시지로 요청한다.

기대 판정이 '미정'인 사례("이게 왜 이렇게 나오지")도 받는다. 그때는 칸을 비워 둔 채 재현하고, 원고를 확인한 뒤 "맞는 판정은 무엇이고 근거는 무엇인가"를 분석 결과로 채운다. 판정은 그대로인데 비고가 틀린 경우(엉뚱한 단어·자리)도 오판정으로 다룬다 — 검수자는 비고를 보고 고친다.

## 2. 재현한다

`.venv`를 켜고, **`.env`는 올리지 않는다.** 표준국어대사전 키가 있으면 차례 ②가 검수 중에 `src/ncs_core/data/action_nouns*.txt`(git 관리 파일)를 고쳐 쓰고, LLM 반출 스위치가 있으면 원고 문장이 외부로 나간다. 재현에는 둘 다 필요 없고, 사례가 그 둘에 달려 있으면 그 사실을 사양에 적는다.

```bash
source .venv/bin/activate
ncs-toc "원고.hwpx" "개발계획서.hwp" --out _workspace/repro     # check 이름: position toc overview knowledge perform teaching evaluation references colophon misc
```

결과 폴더 `_workspace/repro/<코드>_xxxx/`에서 본다.
- `*_검수확인서.json` — 확인서 번호별 종합 판정(사용자가 본 판정은 이것이다)
- `*_<구성요소><번호>_<이름>.json` — 항목별 행(예: `…_차례②_학습내용명_행동명사.json`). 한 항목만 볼 때 가장 빠르다
- `*_전체.json` — 체크리스트 행 전부. `체크`(이름→O/X/△/-), `판정`, `비고`, `region_path`
- `*_진단.json` — 경고, 읽은 개수, 미구현 항목

판정이 어느 **체크**에서 나왔는지 먼저 짚는다. 확인서 한 줄은 여러 행·여러 체크를 접은 것이라, "차례 ③ 부적합"은 실제로는 특정 행의 특정 체크 하나가 X인 경우가 많다.

그다음 **파서가 읽은 것**을 직접 본다. 규칙은 원고가 아니라 `ReviewContext`를 본다 — 원고와 컨텍스트가 다르면 규칙은 죄가 없다.

```python
from ncs_core import load_document
import ncs_toc                                   # 해당 엔진
ms, plan = load_document("원고.hwpx"), load_document("개발계획서.hwp")
ctx = ncs_toc.prepare_review(ms, plan, module_code="LM…")
print(ctx.toc)                                    # 엔진마다 필드가 다르다 — <엔진>/models.py의 ReviewContext 참고
front, body = ctx.manuscript.sections[0], ctx.manuscript.sections[1]   # 앞부분(위치·차례·개요) / 본문
for i, p in enumerate(front): print(i, repr(p))   # 문단이 어떻게 갈렸는지
```

인덱스를 읽을 때 두 가지를 조심한다.
- `sections[0]`·`[1]`은 `normalize_sections`가 맞춘 **앞부분/본문**이고, hwpx 안의 `Contents/sectionN.xml` 번호와 다를 수 있다(표지가 따로 구역인 원고에서는 차례가 `section1.xml`에 있어도 `sections[0]`으로 나온다).
- 컨텍스트 안의 인덱스(예: 차례의 `span`)는 빈 줄을 뺀 목록 기준일 수 있다. 그 값을 만든 파서의 docstring을 확인하고 `sections[k][i]`에 바로 넣지 않는다.

볼 것: 문단이 예상과 다르게 갈리거나 합쳐졌는가, 표 셀이 문단 여러 개로 나뉘었는가, 자동 번호(`ms.numbers`)가 복원됐는가, 사용자 정의 영역 문자(PUA)가 섞였는가, 메모 문단이 본문으로 들어왔는가.

**원고의 실제 구조**는 원본 XML로 확인한다. 컨텍스트가 이상해 보여도 원고가 정말 그렇게 생겼을 수 있다(깨진 상호 참조가 `?`로 저장된 쪽 번호 등).

```bash
python .claude/skills/f02-case-triage/scripts/para_xml.py "원고.hwpx" "찾을 문구"
```

문구가 든 문단의 XML과 그 안의 변경 추적·필드·표·탭 요소를 보여 준다. 찾기는 변경 추적 반영본 기준이다 — 수정본·에디팅완료본은 삭제된 옛 글이 XML에 남아 있어, 원시 XML을 문자열로 검색하면 지워진 구판이 먼저 걸린다. hwp(바이너리)는 이 방법을 쓸 수 없으므로 같은 원고의 hwpx가 있으면 그것으로 본다.

같은 원고의 hwp·hwpx 짝(같은 폴더, 확장자만 다른 파일)이 있으면 둘 다 돌린다. 한쪽만 틀리면 원인은 읽기 층이다. 짝이 없으면 건너뛴다.

**기준 데이터가 판정을 정했는지**도 본다. 행동명사(차례 ②)는 인증키가 없어도 목록에 이미 있는 단어면 확정 판정이 난다.

```bash
grep -n "머리어" src/ncs_core/data/action_nouns*.txt        # rejected에 있으면 키 없이도 X
git log --oneline -S"머리어" -- src/ncs_core/data/           # 언제, 어떤 실행에서 들어갔는가
```

목록에 단어가 아닌 것(기호, 문장 부호가 붙은 조각)이 있으면 예전 검수가 잘못 뽑은 머리어를 사전에 물어 기록한 것이다. 파서 결함(A)과 데이터 오염(C)이 함께 있는 사례다.

## 3. 원인 층을 가른다

이 분류가 분석의 핵심 산출물이다. 층에 따라 누가 무엇을 하는지가 완전히 달라진다.

| 분류 | 판별 질문 | 조치 | 구현 진행 |
|---|---|---|---|
| **A. 읽기·파서 결함** | 컨텍스트(파서 출력)가 원고와 다른가? | `ncs_core`(hwp·hwpx·manuscript) 수정. 여러 엔진에 영향 | 진행 |
| **B. 규칙 결함** | 컨텍스트는 맞는데 규칙의 조건이 스스로 밝힌 의도와 다르게 동작하는가? | 해당 엔진 `rules/` 수정 | 진행 |
| **C. 기준 데이터** | 행동명사 목록·NCS 목록·수준 표에 값이 없거나 틀렸는가? | `src/ncs_core/data/` 보정(스크립트로) | 진행 |
| **D. 판정 기준(정책)** | 규칙은 의도대로 동작했는데, 그 의도가 F02 취지나 현장 판단과 어긋나는가? | 기준 변경 제안. 팀·직능연 합의 대상 | **멈춤 — 합의 필요** |
| **E. 기대 표·테스트 설계 오류** | 원고를 원본과 대조하면 기대가 틀렸는가(조작이 다른 곳에 됐거나 안 됐는가)? | 기대 표 TSV 보정 | 사용자 확인 후 |
| **F. 진짜 지적** | 원고가 실제로 F02를 어겼는가? | 수정 없음 | 없음 |
| **G. 형식 한계** | hwp(바이너리)라 서식·자동 번호·쪽 나눔이 없어서 △인가? | 수정 없음(hwpx 변환 안내) | 없음 |

B와 D를 가르는 법: 규칙 파일의 docstring, `docs/CONSISTENCY_REVIEW.md`의 해당 절, 커밋 메시지에 "이렇게 판정한다"는 의도가 적혀 있고 코드가 그대로면 D다. 의도가 적힌 것과 코드가 다르거나, 의도가 생각하지 못한 양식 변형에서 깨졌으면 B다. 애매하면 D로 본다 — 합의 없이 기준을 바꾸면 다른 담당자의 기대 표와 골든이 조용히 틀어진다.

`docs/CONSISTENCY_REVIEW.md` §5.14의 '합의가 필요한 기준 변경' 목록에 이미 올라 있는 건인지 확인한다. 올라 있으면 D이고 새 분석이 필요 없다.

## 4. 수정 방향을 정한다 (A·B·C만)

- **변형으로 기술한다.** "세분류 칸 문구가 셀 안에서 두 문단으로 갈린 경우"처럼 원고 양식의 변형으로 적는다. 파일명·특정 단어에 기대는 조건은 쓰지 않는다.
- **X는 확신할 때만.** 읽지 못했거나 기준이 없으면 △가 맞다. 오탐(X)을 고칠 때 "적합(O)으로 바꿀 근거가 있는가, △로 내려야 하는가"를 구분해 적는다.
- **반대 방향 피해를 적는다.** 조건을 풀면 무엇을 새로 놓치는가, 조건을 조이면 무엇을 새로 잡는가. 떠올린 반례를 사양에 남기면 구현자가 테스트로 만든다.
- **영향 범위를 센다.** 코어 파서를 고치면 그 함수·패턴을 쓰는 곳을 `grep -rn "함수명" src --include='*.py'`로 찾아 엔진 이름을 적는다. 같은 원고를 그 엔진들로도 돌려(`ncs-knowledge`, `ncs-evaluation` … CLI 이름은 `pyproject.toml`의 `[project.scripts]`) 같은 오염이 다른 항목 비고에 번졌는지 확인한다.
- **골든 영향을 예상한다.** 골든은 `tests/golden/*.json`(합성 원고 6종 × 10엔진 × 개발계획서 유/무)이고, 합성 원고는 `tests/make_fixtures.py`가 만든다. 그 합성 원고에 이번 변형이 들어 있는지 보면 골든이 달라질지 알 수 있다.
- **비고 문구를 바꿀 때**는 메모 원고(`ncs_service/annotate.py`)가 비고에서 `원고 「…」` 꼴로 문구를 꺼내 문단을 찾는다는 점을 고려한다. 꼴을 바꾸면 메모가 총괄 메모로 밀린다.

## 5. 수정 사양을 쓴다

`_workspace/01_analyst_spec.md`. 사례가 여럿이면 사례마다 절을 나누고, 맨 위에 요약 표를 둔다.

```markdown
# 수정 사양 (작성일, 기준 커밋 <git rev-parse --short HEAD>)

| # | 항목 | 원고 | 실제→기대 | 분류 | 구현 |
|---|---|---|---|---|---|
| 1 | 차례 ③ | LM…_hwpx | 부적합→적합 | B 규칙 결함 | 진행 |
| 2 | 개요 ③ | LM…_hwp | 부적합→적합 | D 정책 | 합의 필요 |

## 사례 1. 차례 ③ — (변형을 한 줄로)
- **재현**: 명령, 결과 파일 경로, X가 난 체크 이름
- **원인**: 파일:줄, 무엇이 어떻게 판정으로 이어졌는가. 컨텍스트 출력에서 확인한 사실을 인용
- **분류 근거**: 왜 B인가(D가 아닌가)
- **수정**: 위치(파일·함수), 방법, 쓰지 말아야 할 방법이 있으면 그것도
- **기대 판정 변화**:
  | 원고 | 체크 항목 | 이전 | 이후 |
  |---|---|---|---|
- **달라지면 안 되는 것**: 같은 규칙이 계속 잡아야 하는 경우(반례), 영향받는 다른 엔진
- **테스트로 만들 것**: 합성 입력으로 재현할 구조(원고 문구를 옮기지 말고 구조만)
- **골든 영향 예상**: 없음 / 있음(어느 사례, 판정인지 문구인지)

## 사례 2. 개요 ③ — 합의 필요
- 재현·원인은 같게 쓰고, '수정' 대신 **제안하는 기준**과 **합의할 질문**을 적는다(직능연 이슈 초안으로 바로 쓸 수 있게).
```

'기대 판정 변화' 표는 QA가 실제 변화와 한 줄씩 대조하는 기준이다. 사례 원고뿐 아니라 같은 수정으로 바뀔 것이 예상되는 다른 원고도 아는 만큼 적는다.

## 6. 원고 원문 다루기

원고와 개발계획서는 git 제외 대상이다. 사양(`_workspace/`, 역시 git 제외)에는 문구를 인용해도 되지만, 사양에서 '테스트로 만들 것'은 구조만 적는다. 이슈·PR·커밋에 들어갈 문장은 원고 문구 없이 쓴다.
