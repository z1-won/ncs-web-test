# F02 규칙 수정

수정 사양(`_workspace/01_analyst_spec.md`)을 가장 작은 변경으로 구현한다. 공통 규약은 `docs/CONVENTIONS.md`가 원본이고, 이 문서는 오판정 수정에서 자주 갈리는 판단만 다룬다.

## 1. 어디를 고칠지

| 사양의 분류 | 고치는 곳 | 주의 |
|---|---|---|
| A 읽기·파서 | `src/ncs_core/hwp.py`·`hwpx.py`·`documents.py`·`manuscript/` | 모든 엔진이 쓴다. 고치기 전에 그 함수의 호출처를 `grep`으로 센다 |
| B 규칙 | `src/ncs_<엔진>/rules/<규칙>.py`, 필요하면 같은 엔진의 `patterns.py`·`config.py` | 판정 조건은 규칙에, 양식을 읽는 정규식은 코어 `manuscript/patterns.py`에 |
| C 기준 데이터 | `src/ncs_core/data/` | 손으로 고치지 말고 `scripts/build_*.py`로 만든다. 행동명사의 사람 승격만 목록 파일을 직접 고친다 |

계층 규칙: 엔진은 `ncs_core`만 import한다. 두 엔진이 같은 추출이 필요하면 코어로 올린다. 엔진끼리 import하면 `tests/contract/test_layering.py`가 막는다 — 막히라고 있는 테스트이므로 우회하지 않는다.

`ncs_core`에는 판정 정책을 두지 않는다. "이 경우는 봐준다" 같은 판단이 코어 파서에 들어가면 그 파서를 쓰는 다른 엔진의 판정이 함께 바뀐다. 코어는 원고를 있는 그대로 읽어 주고, 봐줄지는 규칙이 정한다.

## 2. 테스트를 먼저 쓴다

사양의 '테스트로 만들 것'을 합성 입력으로 옮겨, 고치기 전에 실패하는 것을 확인한 뒤 고친다. 고친 뒤에야 쓴 테스트는 "원래 통과하던 테스트"일 수 있다.

- 규칙 함수는 I/O가 없다. 딕셔너리·문단 목록을 직접 만들어 규칙을 부른다. 같은 엔진의 기존 테스트(`tests/test_<엔진>*.py`)가 입력을 만드는 방식을 따른다.
- 문서 구조가 필요하면 `tests/make_fixtures.py`의 합성 HWPX 생성 방식을 쓴다. 기존 픽스처 원고(`tests/fixtures/원고_*.hwpx`)를 바꾸면 골든 전체가 흔들리므로 새 테스트 안에서 따로 만든다.
- **실제 원고 문구를 옮기지 않는다.** `samples/`는 git 제외다. 같은 구조(문단이 갈린 자리, 번호 꼴, 공백 위치)를 가진 지어낸 문구를 쓴다.
- 사양의 '달라지면 안 되는 것'도 테스트로 만든다. 오탐을 고친 수정이 진짜 부적합까지 통과시키지 않는다는 증거가 된다.
- 외부 호출이 걸린 규칙(차례 ② 사전, 수행 ② LLM)은 가짜 resolver를 주입한다. 기존 `tests/engines/test_toc_action_nouns.py`, `tests/core/test_llm.py` 방식.

## 3. 판정과 비고

- 판정은 `ncs_core.verdict(checks)`로만 계산한다(X가 있으면 부적합, X 없이 △가 있으면 판단불가). 판정 문자열을 직접 쓰지 않는다.
- **모르면 △.** 조회 불가·추출 실패·형식 미지원은 X가 아니라 △, 항목이 해당 없으면 `-`. 오탐을 고칠 때 O로 바꿀 근거가 없으면 △로 내린다.
- **체크 이름을 바꾸지 않는다.** 확인서(`<엔진>/sheet.py`의 `SheetItem.check_prefix`)가 체크 이름의 접두(①②…)로 행을 항목에 배정한다. 이름을 바꾸거나 새 체크를 넣을 때는 `sheet.py`를 같이 연다.
- 비고는 검수자와 집필진이 읽는 문장이다. 한국어로, 원고·기준 문구는 「」로 감싸고, 원인은 뒤에 괄호로. 여러 사례는 `ncs_core.notes.lines()`로 줄을 나눈다.
- 비고 꼴에는 소비자가 있다. 메모 원고(`ncs_service/annotate.py`)는 사례 줄에서 `원고 「…」`를 꺼내 그 문구가 있는 문단에 메모를 단다. 원고 문구를 인용하던 비고에서 인용을 빼거나 꼴을 바꾸면 메모가 문단을 못 찾고 총괄 메모로 밀린다.
- `region_path`·`위치`도 메모 원고가 문단을 찾는 데 쓴다. 기존 행과 같은 꼴을 유지한다.

## 4. 골든을 다시 만들지

```bash
source .venv/bin/activate
pip install -e . -q && python -m unittest discover tests
```

기준선(`_workspace/00_input/baseline_tests.txt`)과 비교해 **새로 생긴** 실패만 본다. 수정 전부터 실패하던 테스트는 건드리지 않고 그대로 보고한다.

`tests/contract/test_golden.py`가 깨졌을 때:

| 상황 | 할 일 |
|---|---|
| 사양이 '골든 영향 있음'이라 예고했고, 깨진 사례·방향이 예고와 같다 | `PYTHONPATH=src python tests/make_golden.py` → `git diff tests/golden`을 읽어 판정 변동이 예고와 같은지 확인 |
| 예고와 다른 사례가 깨졌거나, 사양은 '영향 없음'이었다 | 회귀다. 골든을 다시 만들지 말고 원인을 찾는다 |
| 문구(비고)만 바뀌고 판정은 그대로다 | 재생성하되 변경 요약에 '문구만, 판정 변화 0'이라 적는다 |

골든 diff는 "무엇이 바뀌었는지"의 기록이다. 읽지 않고 재생성하면 회귀를 스냅샷에 구워 넣게 된다.

## 5. 문서

- 판정 정책이나 동작을 바꿨으면 `docs/CONSISTENCY_REVIEW.md`의 §5 아래에 다음 번호로 절을 추가한다: 문제 → 조치 → 검증 순, 기존 절(§5.11~5.13)과 같은 분량.
- 검수 범위나 항목 메모가 달라졌으면 `README.md`의 '검수 범위' 표를 고친다.
- 구조만 바꾼 수정은 문서를 건드리지 않는다.

## 6. 스타일

Python 3.10+, 엔진·코어는 표준 라이브러리만. black 스타일에 줄 길이 120, 한 줄에 여러 문장 금지. 모듈 첫 줄은 한국어 docstring. 규칙·파서에서 `print`하지 않고, 오류는 `ValueError`.

## 7. 변경 요약을 쓴다

`_workspace/02_dev_changes.md`:

```markdown
# 변경 요약 (기준 커밋 <short sha>)

## 사례 1. 차례 ③
- **바꾼 파일**: `src/…:함수` — 무엇을 왜
- **추가한 테스트**: `tests/…::테스트 이름` — 무엇을 재현하는가 (고치기 전 실패 확인: 예/아니오)
- **골든**: 재생성 안 함 / 재생성(바뀐 사례 N건, 판정 변동 요지 또는 '문구만')
- **문서**: 갱신한 절
- **사양과 다르게 한 것**: 없음 / 있음(이유)

## 테스트 결과
전체 N건, 실패 M건(기준선 대비 새 실패 K건)

## 발견한 다른 문제
(이번에 고치지 않은 것)

## 커밋 메시지 제안
FIX: 차례 ③ …        ← .gitmessage 규칙: TYPE: 무엇을 — 한국어 50자 안팎, 항목 이름 포함
```

TYPE은 FIX(오판정 수정), DATA(기준 데이터·기대 표), TEST, REFACTOR, DOCS 중에서 고른다. 문구만 바꿨으면 제목 끝에 '문구만, 판정 변화 0'을 붙이는 것이 이 저장소의 관례다. 커밋은 하지 않는다.
