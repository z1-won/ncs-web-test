# F02 오판정 수정 루프

검수 판정이 기대와 다른 사례를 받아, 원인을 가르고(분석) → 고치고(구현) → 의도한 판정만 바뀌었는지 확인(검증)한 뒤
판정 변화 표와 커밋 메시지 제안까지 내는 워크플로우다.

## 실행 모드: 서브 에이전트

분석 → 구현 → 검증이 순차로 이어지고 각 단계의 산출물이 파일로 넘어가므로, `Agent` 도구로 한 명씩 부르고 반환값과 파일로 결과를 받는다.
검증자가 구현자와 대화하지 않는 것은 의도다 — 검증은 사양과 결과만 보고 독립적으로 판단해야 한다.

## 에이전트 구성

| 에이전트 | subagent_type | 역할 | 스킬 | 출력 |
|---|---|---|---|---|
| case-analyst | `case-analyst` | 재현, 원인 층 분류, 수정 사양 | f02-case-triage | `_workspace/01_analyst_spec.md` |
| engine-dev | `engine-dev` | 사양대로 구현, 합성 입력 테스트 | f02-rule-fix | 작업 트리 변경 + `_workspace/02_dev_changes.md` |
| verdict-qa | `verdict-qa` | 테스트·골든·배치 전후 대조, 합격/반려 | f02-verdict-verify | `_workspace/03_qa_report.md`, `_workspace/03_qa_verdict_changes.md` |

모든 `Agent` 호출에 `model: "opus"`를 준다. 커스텀 타입을 못 찾는 세션이면(에이전트 파일을 만든 직후 등) `subagent_type: "general-purpose"`로 부르고
프롬프트 첫 줄에 "`.claude/agents/<이름>.md`를 읽고 그 역할과 원칙대로 일하라"를 넣는다.

## 워크플로우

### Phase 0: 컨텍스트 확인

`_workspace/`가 있는지 보고 실행 모드를 정한다.

| 상태 | 모드 | 할 일 |
|---|---|---|
| `_workspace/` 없음 | 초기 실행 | Phase 1부터 |
| 있음 + 같은 사례에 대한 후속 요청("검증만 다시", "사양 고쳐서 다시", "반려된 것 고쳐줘") | 부분 재실행 | 해당 Phase의 에이전트만 다시 부른다. 프롬프트에 이전 산출물 경로와 사용자 피드백을 넣는다 |
| 있음 + 새 사례 | 새 실행 | `_workspace/base` 작업 트리가 남아 있으면 `git worktree remove`로 먼저 정리하고, `_workspace/`를 `_workspace_{YYYYMMDD_HHMMSS}/`로 옮긴 뒤 Phase 1부터 |

부분 재실행에서 어디부터 다시 할지: 사양이 바뀌면 구현·검증도 다시, 구현만 바뀌면 검증도 다시, 검증만 요청이면 검증만.

### Phase 1: 준비 (오케스트레이터가 직접)

1. 사용자 입력에서 사례를 뽑아 `_workspace/00_input/case.md`에 적는다. 사례마다 구성요소·번호, 원고(와 개발계획서) 경로, 실제 판정, 기대 판정, 기대의 근거.
   대조 결과 파일(`batch_compare.py` 출력)을 받았으면 미탐·오탐 후보·원본 자체 부적합 줄을 사례로 옮긴다. 원고 경로를 못 찾으면 `samples/`를 먼저 찾아보고, 없으면 사용자에게 묻는다.
2. 배치 검증에 쓸 원고 폴더(`--root`)를 정한다. 사용자가 준 폴더 → 사례 원고가 든 폴더 순. `case.md`에 함께 적는다.
3. 작업 트리가 깨끗한지 `git status --short`로 본다. 사용자의 미커밋 변경이 있으면 이번 수정과 섞이므로 알리고 진행 여부를 확인받는다.
4. 기준선 테스트를 돌려 저장한다. 수정 전부터 실패하는 테스트를 이번 변경 탓으로 돌리지 않기 위해서다.
   ```bash
   source .venv/bin/activate && pip install -e . -q
   python -m unittest discover tests > _workspace/00_input/baseline_tests.txt 2>&1; git rev-parse HEAD >> _workspace/00_input/baseline_tests.txt
   ```

사례가 다섯 건을 넘으면 같은 엔진·같은 증상끼리 묶어 사용자에게 처리 순서를 제안한다. 한 루프에 여러 원인을 섞으면 판정 변화의 원인을 가를 수 없다.

### Phase 2: 분석

```
Agent(subagent_type: "case-analyst", model: "opus", description: "오판정 원인 분석",
      prompt: "_workspace/00_input/case.md의 사례를 분석해 _workspace/01_analyst_spec.md를 써라. …")
```

서로 다른 엔진의 독립된 사례가 여럿이면 사례 묶음별로 `run_in_background: true`로 동시에 부르고, 출력 파일을 `01_analyst_spec_<엔진>.md`로 나눈 뒤 오케스트레이터가 하나로 합친다.

**분류 관문.** 사양의 요약 표를 읽고 분류별로 갈래를 탄다. 이 관문이 이 루프에서 가장 중요한 판단이다.

| 분류 | 다음 |
|---|---|
| A 읽기·파서, B 규칙, C 기준 데이터 | Phase 3으로 |
| D 판정 기준(정책) | **구현하지 않는다.** 제안 기준과 합의할 질문을 사용자에게 보여 주고, 원하면 '직능연 📋' 라벨 이슈 초안으로 정리한다. 사용자가 "합의됐다, 진행"이라고 하면 그때 Phase 3 |
| E 기대 표 오류 | 근거(원본과의 대조)를 보여 주고 기대 표 TSV를 고칠지 확인받는다. 고치면 DATA 변경으로 Phase 3 |
| F 진짜 지적, G 형식 한계 | 수정 없음. 근거를 보고하고 그 사례는 종료 |

정책을 합의 없이 바꾸지 않는 이유: 3인이 엔진을 나눠 맡고 기대 표와 골든을 공유한다. 한 사람이 기준을 바꾸면 다른 담당자의 기대 판정이 조용히 틀어지고, 직능연과 맞춘 기준에서 벗어날 수 있다.

진행할 사례가 하나도 없으면 Phase 5로 건너뛴다.

### Phase 3: 구현

```
Agent(subagent_type: "engine-dev", model: "opus", description: "규칙 수정 구현",
      prompt: "_workspace/01_analyst_spec.md에서 '구현: 진행'인 사례를 구현하고 _workspace/02_dev_changes.md를 써라. 진행 대상: 사례 1, 3. …")
```

구현자는 같은 작업 트리를 고치므로 한 번에 한 명만 부른다. 반환 메시지에 '사양과 다르게 한 것'이나 '구현하지 않은 사양 항목'이 있으면 Phase 4로 가기 전에 읽고, 사양 문제면 분석가를 다시 부른다.

### Phase 4: 검증

```
Agent(subagent_type: "verdict-qa", model: "opus", description: "판정 변화 검증",
      prompt: "작업 트리의 변경을 검증해 _workspace/03_qa_report.md와 03_qa_verdict_changes.md를 써라. 배치 원고 폴더: <root>. …")
```

반환 메시지 첫 줄로 갈래를 탄다.

| 결과 | 다음 |
|---|---|
| 합격 | Phase 5 |
| 합격(배치 미검증) | Phase 5. 보고에 실제 원고 대조를 못 했다는 것과 그 이유를 분명히 적는다 |
| 반려 | 반려 사유를 넣어 `engine-dev`를 다시 부르고(Phase 3), 다시 검증한다. **두 번까지.** 세 번째 반려면 멈추고 사양·변경·반려 사유를 사용자에게 보여 준다 |
| 반려 + '사양 재검토 필요' | `case-analyst`를 반려 사유와 함께 다시 부른다(Phase 2) |

반복에 한도를 두는 이유: 같은 반려가 되풀이되면 구현 솜씨가 아니라 사양이나 기준의 문제이고, 그것은 사람이 볼 일이다.

### Phase 5: 보고와 정리

1. `_workspace/base` 작업 트리가 남아 있으면 `git worktree remove _workspace/base`.
2. 사용자에게 보고한다. 순서대로:
   - 사례별 결과: 분류, 조치(수정함 / 합의 필요 / 수정 불필요), 한 줄 원인
   - 판정 변화 표(`_workspace/03_qa_verdict_changes.md` 내용 — PR 템플릿의 '판정 변화' 절에 그대로 붙일 수 있다)
   - 테스트: 새 실패 수, 기존 실패가 있으면 그것도
   - 미검증으로 남은 것
   - 합의가 필요한 건의 질문 목록
   - 커밋 메시지 제안(`.gitmessage` 규칙)
3. `_workspace/`는 지우지 않는다(사후 확인용, git 제외).
4. **커밋·푸시·PR은 사용자가 요청할 때만 한다.**
5. 피드백을 묻는다: "결과나 진행 방식에서 바꾸고 싶은 점이 있나요?" 같은 유형의 피드백이 반복되면 해당 스킬·에이전트 정의를 고치고 `.claude/CLAUDE.md`의 변경 이력에 적는다.

## 데이터 흐름

```
사용자 사례 ─→ [오케스트레이터] ─→ _workspace/00_input/case.md, baseline_tests.txt
                                         │
                                  [case-analyst] ─→ 01_analyst_spec.md ─→ 분류 관문 ─→ (D·E·F·G는 사용자에게)
                                         │ A·B·C
                                  [engine-dev]   ─→ 작업 트리 변경 + 02_dev_changes.md
                                         │                    ↑ 반려(최대 2회)
                                  [verdict-qa]   ─→ 03_qa_report.md, 03_qa_verdict_changes.md
                                         │ 합격
                                  [오케스트레이터] ─→ 보고(판정 변화 표, 커밋 메시지 제안)
```

에이전트 사이의 전달은 모두 파일이다. 프롬프트에는 읽을 파일 경로와 이번 호출의 범위(어느 사례, 재작업이면 반려 사유)만 넣는다.

## 지켜야 할 것

- **원고 원문은 저장소에 들어가지 않는다.** `samples/`와 `_workspace/`는 git 제외다. 테스트·문서·커밋 메시지·PR 본문에 원고 문구를 옮기지 않는다. PR용 표에는 비고를 넣지 않는다.
- **`.env`를 올리지 않고 돌린다.** 사전 키는 검수 중에 git 관리 데이터 파일을 고치고, LLM 반출 스위치는 원고 문장을 외부로 보낸다. 사례가 그 둘에 달려 있으면 사용자에게 알리고 승인받은 뒤에만 올린다.
- **화면·API·DB는 범위 밖이다.** 수정이 `src/ncs_web`, `frontend/`, 마이그레이션에 닿아야 하면 멈추고 사용자에게 알린다.

## 에러 핸들링

| 상황 | 대응 |
|---|---|
| 에이전트가 산출물 파일 없이 끝남 | 같은 프롬프트로 1회 다시 부른다. 또 실패하면 그 단계에서 멈추고 반환 메시지를 사용자에게 보여 준다 |
| 분석가가 '재현 불가' | 사용자에게 재현 명령과 결과를 보여 주고, 원고·버전이 맞는지 확인받는다 |
| 원고 폴더가 없어 배치 대조 불가 | 검증은 테스트·골든·경계면까지만. 보고에 '배치 미검증' 명시 |
| 기준선 테스트가 이미 실패 | 그대로 진행하되 보고에 기존 실패 목록을 적는다. 고치지 않는다(범위 밖) |
| 구현 중 골든이 예고 없이 깨짐 | 구현자가 회귀로 보고하고 멈춘다 → 분석가를 다시 불러 영향 범위를 재검토 |
| 세 번째 반려 | 루프를 멈추고 사람에게 넘긴다 |
| `git worktree add` 실패 | 남은 작업 트리(`git worktree list`)를 확인해 `_workspace/base`를 정리하고 재시도. 그래도 안 되면 배치 대조를 미검증으로 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "samples/aiot의 AIoT 원고에서 위치 ②가 부적합으로 나오는데 세분류명은 맞게 적혀 있어. 고쳐줘."
2. Phase 1: `case.md`에 사례 1건, 배치 root = `samples/aiot`, 기준선 테스트 저장.
3. Phase 2: 분석가가 재현 → 세분류 칸이 셀 안에서 두 문단으로 갈려 공백이 끼어든 것을 확인. 문단을 잇는 방식의 결함이면 A, 공백 무시 비교라는 기준 변경이 필요하면 D로 분류.
4. A라면 Phase 3: 구현자가 합성 표로 실패하는 테스트를 쓰고 수정, `02_dev_changes.md` 작성.
5. Phase 4: QA가 수정 전·후 배치를 돌려 '위치 ② 부적합→적합' 1건이 사양과 일치함을 확인, 새 테스트 실패 0 → 합격.
6. Phase 5: 판정 변화 표와 `FIX: 위치 ② …` 커밋 메시지 제안을 보고. 커밋은 하지 않음.

### 정책 갈래
1. 같은 사례에서 분석가가 D(정책)로 분류 — 규칙은 '띄어쓰기만 달라도 부적합'이라는 의도대로 동작했다.
2. 오케스트레이터가 구현을 멈추고, 제안 기준("세분류명은 공백 무시 비교 + 참고 비고")과 합의할 질문을 사용자에게 보여 준다.
3. 사용자가 "팀에서 합의됐어, 진행해"라고 하면 부분 재실행으로 Phase 3부터 이어 간다.

### 에러 흐름
1. Phase 4에서 QA가 반려: 사양에 없는 '필요 지식 ③ 적합→부적합' 2건(코어 파서 변경이 번짐).
2. 오케스트레이터가 반려 사유를 넣어 구현자를 다시 부름 → 구현자가 변경 범위를 좁힘 → 재검증.
3. 다시 반려되고, 세 번째에도 반려면 루프를 멈추고 사양·변경 요약·반려 사유를 사용자에게 보여 준다.
4. 보고에 "미해결: 필요 지식 ③ 회귀 원인 불명"을 명시한다.
